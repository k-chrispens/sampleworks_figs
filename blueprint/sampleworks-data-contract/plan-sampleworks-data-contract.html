Sampleworks evaluation data contract

I want to establish a reasonable data contract for what needs to come in from sampleworks and what we process here. I would like it to follow the principles of parse, don't validate, as well as the tidy data principles from Hadley of the R project. Right now, you can see some of the existing output CSVs from sampleworks in the results folder.

I want to figure out a way to design a robust contract so that we don't have to write a bunch of validation in this repository, but that we can also be flexible in the upstream repository. The way I'm thinking about this is using some sort of Polars data frame situation, or potentially just having data classes in the upstream sampleworks repo for evaluation. Maybe that should be a standard that's agreed upon, but ideally, there are certain things that we're always going to have.

We're always going to have a model and the relevant checkpoint, etc., and any other details about that model's specific run. We're going to have a set of guidance parameters that are specific to a guidance method. And then we're also going to have the experimental data that was used to run that specific sampleworks run.

So, for example, in one case, we might have Boltz-2, which was run with the MD method conditioning flag. That's a Boltz-specific model setup flag. We might have a specific checkpoint that's associated with it. We might then also have a set of guidance weights for running diffusion posterior sampling, so we might just have a given guidance weight. Then we would have the protein that this was run with, or rather, not the protein, actually the mmCIF file that was provided as input, as well as the experimental data file that was provided.

The experimental data, in the long term, could actually be many different files that are all being used in the guidance run. Then we're going to have a separate set of observation variables. For example, in the case of the RSCC evaluation, there would be a column for RSCC, and there actually would need to be a separate RSCC value for each different altloc segment.

There will be different sorts of setups for these evaluations. Some of them will be specific to the individual altloc segments, like the subset of the protein that we're looking at that has multiple conformations. In other cases, we will not have that, and we'll be looking at a protein aggregate measure or a measure over a specific experimental data set, or something like that.

So these are all the various things that I'm thinking about, and I want to try and develop some sort of reasonable contract that works here between the sampleworks repository, which will be producing the evaluation data files and the sets of observations, and the current repository, which is producing interactive figures for analyzing the data. We should also envision that this repository is going to evolve with the types of figures that we want to build.

This repository should accept data that is provided in the specific tidy contract and be able to produce reasonable figures from any sorts of evaluation that you might pass to it.

Overview

  • One consumer-owned package: add sampleworks-contract, imported as sampleworks_contract, in a separately buildable contract/ subproject. Sampleworks depends on a pinned contract release or revision. Neither installing nor importing it loads notebooks, matplotlib, local results, or paper-specific style constants.

The package returns parsed datasets, not booleans that callers must remember to check. Cross-table and scientific checks not expressible in schema declarations remain centralized boundary logic.
  • Tidy at an explicit grain: distinguish executions, artifacts, evaluation executions, regions, reference conformations, and metric-family observations. Model/guidance grid axes are run metadata, not a universal observation identity. Do not replace all metric columns with a generic metric-name/value table or all scopes with nullable columns.

Plot compatibility requirements belong to plotting adapters. No discovery machinery, arbitrary expressions from manifests, or executable imports named by input data.

Expected behavior

Bundle and extension rules

  • A bundle has a JSON manifest and named Parquet tables. The manifest declares the contract version, export identity, available metric families/versions, producer provenance, and relative table locations. Input tables are data, never code.
  • The manifest lists tables actually present; absence means no observations supplied, not an implicit failure, zero, or empty successful evaluation. An unsupported required contract/family version produces a clear error. Do not guess compatibility from matching column names.
  • Known table schemas are explicit. Check unexpected columns before Dataframely validation, which otherwise removes them. Preserve upstream-specific configuration in designated, namespaced configuration fields rather than silently discarding columns or widening schemas during import.
  • Model and guidance configurations carry method/type identifiers, configuration versions, and resolved JSON objects. Typed parsing of recognized methods exposes analyzable parameters. Unknown method configuration remains preserved provenance, but does not gain fabricated typed plotting axes.
  • Do not stringify observation arrays: predicted occupancy and per-altloc RMSD/counts use rows with explicit conformation identifiers. Structured configuration is metadata, not an excuse to hide repeated measurements in JSON.
  • Parquet files alone do not prove key uniqueness, foreign keys, finiteness, or scientific equivalence. Parsing establishes these guarantees once; serialization carries versions and definitions, not a magical persistent type proof.

Selection interpretation is part of provenance

  • Store original selection text, selection language/dialect and version, reference artifact and selected data block(s), chain namespace (label_asym_id versus auth_asym_id), residue namespace (label_seq_id versus auth_seq_id), insertion-code handling, model-number restriction, and altloc/atom filters.
  • For new exports, Sampleworks resolves selections against the referenced mmCIF and exports explicit membership. Canonical atom locators are (artifact_id, data_block_id, atom_site_id): _atom_site.id is unique within its data block's atom-site list, not necessarily across a file. Retain atom-site IDs as strings, plus model number and both author/label identifiers for explanation and residue-level analysis. Model number does not replace data-block scope.
  • Resolve reference conformations separately from the union of a region's atoms. Conformation-membership rows explicitly enumerate chosen alternatives and included shared/blank-altloc atoms using the same scoped atom locators. New resolved exports require membership within the declared region/reference scope; a local A/B label alone is insufficient.
  • Do not infer joint states for independently alternate sites. A compound region containing two A/B sites does not establish AA/AB/BA/BB states, correlations, or joint occupancies. Preserve separately evaluated local regions, or export only joint states that the producer actually defines with resolved membership and supporting provenance.
  • Distinguish scored atoms from alignment anchors. Sampleworks can align using shared atoms outside the scored region; export both resolved sets and any reference preprocessing rather than widening the reported measurement region to include all anchors.
  • Do not equate author and label numbering, discard insertion codes, assume chain IDs are one character, infer atom membership from a display range, or require label sequence IDs for nonpolymer atoms.
  • Legacy unresolved selections or reference conformations remain explicitly unresolved. They can be displayed and retained, but operations requiring proven region equality or reference-state alignment report the missing guarantee rather than guessing a data block, numbering namespace, or shared-atom rule.

Metric families and supporting data

  • Each family declares its versioned scientific definition, row grain, target/reference relationships, named measurement columns, units, and improvement direction where meaningful. Schemas define column dtypes and primary keys once; grain documentation explains their scientific interpretation.
  • Each family has a separate outcome table at its own attempted-measurement grain. Outcomes carry attempt ID, evaluation ID, family-specific scope keys, status, and failure/not-applicable reason. Successful measurement rows reference successful attempts; failed attempts cannot acquire invented numerical values.
  • Scopes do not all require runs: reference classification and training-cluster assignment are legitimate evaluations of reference data. Avoid forcing a fake model/checkpoint onto those observations.

Parsing, composition, and unknown provenance

  • Parsing checks supported versions, expected columns, schema rules, identity uniqueness, foreign keys, evaluation outcomes, and family scope consistency. Collect lazy validation before returning a dataset represented as successfully parsed. Never use Dataframely soft-filtering to silently salvage rows.
  • Typed frame annotations alone do not prevent arbitrary Polars mutation. Package parsed-bundle construction is internal; expose query/projection operations that do not silently preserve invalid guarantees. Re-establish invariants at composition and export boundaries, not inside every plot.
  • Compatible bundles may contain different models, guidance grids, reference contexts, and evaluator definitions. Composition preserves those distinctions; comparison eligibility is evaluated separately. It does not force measurements onto a complete Cartesian product or manufacture missing rows.
  • A parsed observation bundle can preserve independent repeat runs without pairing them. Construction of an analysis dataset at a requested comparison grain is a separate explicit boundary: reject unresolved repeats before returning that dataset. Require declared seed/replicate mapping, an explicit run selection, or an explicit retained repeat dimension; timestamps identify executions but do not establish pairings between them.
  • Use Diffly on intersecting primary keys to explain differences and Polars to perform explicit unions. Append new keys, deduplicate exact scientific observations, and reject conflicting values or scientific identity metadata. Merge location/source annotations separately so relocated files do not create measurement conflicts.
  • Equality for deduplication is exact after canonical schema parsing. Numerical tolerances are reporting tools, not permission to replace different measurements. Preserve independent runs/re-evaluations rather than deduplicating on model, guidance, and protein labels.
  • Unknown IDs are scoped to a source export/import identity; repeated import of the same retained source identity is idempotent. Two unknown checkpoints, references, or numbering schemes are not equal merely because both are missing. Do not infer cross-export duplicate execution identity from configuration resemblance.
  • Legacy import reports missing facts and supports saved user-supplied provenance, including Sampleworks revision/version and a source description. Interactive skill usage asks for available context; library parsing remains noninteractive, emitting warnings and returning a structured provenance report. Require specific missing facts only for operations needing them.
  • Raw legacy artifacts remain unchanged. Legacy import is an explicit adapter, never a path-guessing fallback in the standard parser. Model overrides and historical path conventions remain isolated and visible in the import report.

Plot compatibility without automatic scientific inference

  • A small requirement description states needed family/definition, measurement columns, units, grain, reference alignment, provenance guarantees, pairing keys, and any explicit reduction. Proven structural alignment requires data-block-scoped atom membership; conformation-resolved comparisons also require resolved reference-state membership, not matching A/B labels. Return compatible/incompatible with actionable reasons, including matched/unmatched counts.
  • Users select baseline/reference configurations. Known-method defaults are explicit suggestions, not hidden weight-zero behavior; heterogeneous configuration fields are exposed as typed axes only for recognized configuration schemas.
  • Before constructing a comparison dataset, require equal intended cohort/reference scope and explicit seed/replicate mapping where repeats exist. Detect ambiguous one-to-many pairings and empty intersections, and block construction rather than merely warning at plot time. Preserve all source observations; never allow an accidental many-to-many join or silently average replicates.
  • Initial deliverable includes requirement examples for distributions, paired baseline-versus-guided comparisons, and guidance trajectories. It does not auto-render arbitrary metrics, port all figures, or embed plot callbacks into the metric registry.
